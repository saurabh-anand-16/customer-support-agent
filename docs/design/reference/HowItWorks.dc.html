How it works

The model reads and writes words. Code decides eligibility, money and every change to an order.

The whole project at a glance

Arrows show who calls whom. Dashed boxes are optional or offline. The models only read and write words. Everything that changes data goes through code.
  1. 1
    The session fixes who you are
    The customer is chosen on the Home page. Nothing typed in the chat can change it, and the model never sees the customer id.
  2. 2
    The router picks a lane
    One model call labels the message: order status, policy question, return or replace, cancel, human help, out of scope, or unclear. Off-topic and tricky messages get a fixed reply and stop here.
  3. 3
    The lane uses a few read-only tools
    It can look up orders, check eligibility, and search the policy pages. The tools that change data are not available to the model.
  4. 4
    Policy answers cite their passages
    The search returns passages from the policy pages. The citations shown under an answer are written by code from those passages, not by the model.
  5. 5
    You confirm, then code makes the change
    A return or cancel is shown as a card. Only after you answer yes does code write it, using the customer from the session. A no, a change, or an unclear answer writes nothing.
  6. 6
    The answer check compares numbers with the tools
    Every amount, number and date in a reply must appear in a tool result from that turn. If not, the agent retries once, then uses a plain template built from the tool data.
  7. 7
    Exceptions go to a person
    A high-value order, a restricted account, or a late request is queued with the conversation and the eligibility result. A manager approves or declines. The next time you write, the agent tells you the outcome.
Four rules that do not bend
The model never sees the customer id.
Only code changes an order.
Numbers must come from a tool.
Exceptions go to a person.
